FAQ — real problems, real fixes

Every one of these actually happened while building and running this board — so a new user will likely meet some of them too. Click a question to open it.

+ Docker build dies at RUN npm run build — “Unable to resolve @typescript/typescript-linux-arm64” docker

TypeScript 7 ships its native compiler as per-platform optional npm packages. When npm ci runs inside the image over a slow/flaky Docker-VM network, npm silently skips optional packages — then tsc can’t find its Linux binary.

Fix: deploy with ./scripts/start-jira-board.sh — it builds dist/ on your machine first and tells Docker to just package it (DIST_SOURCE=prebuilt). Building by hand:

npm run build
docker compose build --build-arg DIST_SOURCE=prebuilt

BuildKit collapses the real error — rerun with docker build --progress=plain . to actually see it.

+ The deploy “hangs” for 10+ minutes with no output docker

Docker Hub pulls can crawl from the Docker VM (~80 KB/s seen here), and --pull re-fetches the base image on every build. The start script deliberately does not use --pull — keep it that way, keep the node base image cached, and never Ctrl-C mid-pull (the download is discarded).

+ I redeployed and the board came up empty data

Compose bind-mounts ./jira-intern from the folder you deploy from — your ticket data lives wherever you last deployed. Deploying from a fresh clone/folder points the container at an empty directory.

Fix: find the old data and copy it over before deploying from the new folder:

docker inspect JIRA-Board --format '{{range .Mounts}}{{.Source}}{{"\n"}}{{end}}'
# then copy data.json, data.js, .state.json, cache/, reports/ from that
# jira-intern/ into the new folder's jira-intern/ and redeploy

Or simply press Refresh board and rebuild the Completed archive — everything is re-fetchable from Jira, it just takes longer.

+ npm ci fails: “Your cache folder contains root-owned files” docker

An old npm bug left root-owned files in ~/.npm. Either fix the ownership (the command npm prints) or sidestep with a throwaway cache:

npm ci --cache "$TMPDIR/npm-cache"
+ The Raised chip is missing (or shows nothing) board

The raised-by-me list is fetched by the board refresh — a brand-new deployment has none yet. Click Refresh board once (or the Hard refresh button inside the Raised view). The chip hides itself while the list is empty, and the whole feature can be toggled in Settings → Raised by me.

+ AI briefs aren’t appearing on tickets board

Three usual causes, in order: Settings → AI usage is set to None (deterministic mode — no briefs by design); the AI-Intern container is down (Settings shows its health); or it simply hasn’t gotten there yet — the summarize pass writes up to 8 briefs per run, so a full board fills in over a few scheduled passes. Raised tickets queue after active ones.

+ “Jira MCP unavailable — showing last known state” / fetch keeps failing network

Either the VPN is down (on-prem Jira is only reachable on it) or the token expired (Jira returns 401). Test the token directly (set JIRA_PERSONAL_TOKEN and JIRA_URL in your shell first):

curl -sk -H "Authorization: Bearer $JIRA_PERSONAL_TOKEN" \
  "$JIRA_URL/rest/api/2/myself" | head -c 200

A JSON blob with your name = token fine, look at the VPN. HTML or 401 = make a new Personal Access Token and paste it over the old one with the key button in the board header.

+ “Skipped — another refresh/archive was already running” data

Only one job may write data.json at a time (lock files keep the daily fetch, the archive rebuild, per-ticket refreshes and the raised refresh apart). Wait for the running job — the header button shows its live progress. A stale lock from a killed run clears itself once its owner process is gone.

+ A ticket’s PR badge looks stale (merged PR still shows open) data

Review activity happens in Bitbucket and never bumps the Jira ticket’s “updated” time, so the fast path can carry an old badge. Use the per-ticket refresh button on the card (or in its drawer). If Bitbucket itself is unreachable, PR data is deliberately carried forward rather than wiped — the run note in the footer says so.

+ Port 4321 is already in use network

./scripts/start-jira-board.sh reclaims the port automatically (it stops whatever holds it, including stale containers from older compose projects). Manual alternatives:

docker compose down
PORT=8080 bash scripts/start-jira-board.sh   # or run on another port
