1 · The API keys dialog

Every token the board uses is added in the board itself — no file to edit. Click the key button in the header, beside Settings (it shows an amber dot while the Jira token is missing; a new install shows Add API keys first instead). The window works like Settings: a sidebar groups the services (Atlassian · Code hosting · CI/CD & security · AI models, A–Z inside each); a service is lit in its colour once its keys are saved, and the selected one fills the panel beside it.

  • Pick a service to see why it is needed, what uses it, and where to get the key.
  • Paste the value and Save. A secret comes back masked (first and last few characters only); URLs, e-mail addresses and user names are shown in full.
  • Saving a key never removes another one — a token goes only when you press Remove.
  • Keys marked Not used yet can be saved now for an integration that is coming.
  • Test (in an open row, once its keys are saved) checks the saved key against its host with one read-only call and shows the answer inline: ✓ Connected with who you are signed in as, Key rejected (401), Can't reach host, a certificate problem, or what is still missing. A coloured dot stays on the row.
  • Behind a corporate proxy: the Test button's cloud checks (Claude, OpenAI, Gemini, Cursor, GitHub) do not go through HTTPS_PROXY — the board's server calls them directly — so where the internet is reachable only through a proxy they may say Can't reach host even though the key is fine and the AI calls themselves work.
  • A key works from the next fetch or AI call — no restart. Remove (asks twice) clears it.
Keys are written to setup/.env in your copy of the repository — git-ignored, kept out of the Docker image and never served to the browser. Running without the board? Create that file yourself with KEY=value lines (chmod 600); the names are below.

3 · Connect Jenkins

1

Save your Jenkins user and API token

In Jenkins: your name → Configure → API Token → Add new token. In the board's key dialog, open Jenkins and save your user name and the token.

2

List your multibranch jobs in your personal config

Add a jenkins block to ~/.ai/config.json — one job URL per repository and environment. Keys are the repository slugs; the URLs below are placeholders.

"jenkins": {
  "jobs": {
    "payments-service": {
      "qa":  "https://jenkins.example.com/job/team/job/payments-service-qa/",
      "uat": "https://jenkins.example.com/job/team/job/payments-service-uat/"
    }
  }
}

Job URLs must start with https:// — an http:// one is skipped (your token is sent with every call), and the fetch log says so. The certificate is always checked; a company certificate goes in ~/.ai/ca-bundle.pem (page 09). Only as a last resort, JENKINS_INSECURE_TLS=1 in your shell before deploying (or in setup/.env) turns checking off for Jenkins alone — JIRA_INSECURE_TLS does not apply to Jenkins.

Repositories not listed are never asked. The board reads the latest build of each of a ticket's own branches per environment: result, number, tests, failing test names, the failed stage and the deploy target. Full reference: CONFIG.md and INTEGRATIONS.md.

3

Refresh

Click Refresh. Builds are re-read on every refresh, even for tickets that did not change in Jira.

4 · Connect Checkmarx One

1

Save the API key and tenant URL

In Checkmarx One: Identity and Access Management → API Keys. In the key dialog, open Checkmarx One and save the key and your tenant API URL (https, for example https://your-tenant.cxone.cloud). Add the token URL only when your sign-in host differs from the API host.

2

Which tickets are checked

Only vulnerability-fix tickets with a pull request — ones whose title, type, labels, description or acceptance criteria mention a CVE, Checkmarx, SAST / SCA, a CWE or a dependency upgrade. For each CVE, query, CWE, result link or package the ticket names, the board compares the latest scan of the PR's branch with the base branch's scan and says Fixed, Open, Not found (in neither scan — check the id) or Unknown (no scan to compare yet).

6 · Troubleshooting

Start with the Test button in the service's row: it tells you straight away whether the saved key and URL work.

SymptomFix
Test says Key rejected (401)The host answered but refused the key: it was mistyped, has expired or was revoked. Create a new one and Save it. Atlassian Cloud also needs the account e-mail.
Test says Access denied (403)The key is valid but lacks permission for that read — give the token read access (Bitbucket: project read; Jenkins: Overall/Read and Job/Read).
Test says Can't reach hostThe board's server cannot reach that address: VPN off, a typo in the base URL, or (in Docker) no route from the container. Hover the result to see the host and the error.
Test says Certificate not trustedThe host uses a company certificate. Put the company root CA in ~/.ai/ca-bundle.pem (or point JIRA_CA_BUNDLE at it) — see page 09.
Test says Not found (404) or Redirected to …The base URL points at the wrong place, or at a sign-in page. Use the API host itself (for Jira, the address you see before /browse/).
Test says Not configuredIt names what is missing — a key, the base URL (the dialog or endpoints.* in your config), or a Jenkins job URL in jenkins.jobs.
No build chipsAre both Jenkins keys saved and the repository listed in jenkins.jobs with an https job URL (http ones are skipped)? Is the branch name in the ticket's PR or branch list? A branch with no build simply shows nothing.
"Jenkins unreachable — builds carried forward"The container can't reach Jenkins or the token was refused (401/403). Check VPN / DNS, the token, and a company certificate in ~/.ai/ca-bundle.pem (page 09). The last known builds stay on the cards, marked stale in their tooltip, and the report's CI gate says Not verified until Jenkins is read again.
"Checkmarx unreachable — vulnerability results carried forward"Check the API key, that the base URL is https, and the token URL if your sign-in host is separate. Previous results stay.
Every target says UnknownThe PR's branch has no completed scan yet (or none that ran SCA for CVEs / packages, SAST for queries), the base branch has none, the branch was last scanned before the base (rescan it), the ticket names a per-scan result id instead of a similarity id, or no Checkmarx project is named exactly like the repository.
A key row stays grey after SaveA required key of that service is still empty, or saving failed — see "could not write setup/.env" on page 09.
