1 · The API keys dialog

Every token the board uses is added in the board itself — no file to edit. Click the key button in the header, beside Settings (it shows an amber dot while the Jira token is missing, and turns orange or red when a saved key's latest call failed; a new install shows Add API keys first instead). The window works like Settings: a sidebar groups the services (Atlassian · Code hosting · CI/CD & security · Observability · AI models, A–Z inside each); a service is lit in its colour once its keys are saved, and the selected one fills the panel beside it.

  • Pick a service to see why it is needed, what uses it, and where to get the key.
  • Paste the value and Save. A secret comes back masked (first and last few characters only); URLs, e-mail addresses and user names are shown in full.
  • Saving a key never removes another one — a token goes only when you press Remove.
  • Keys marked Not used yet can be saved now for an integration that is coming.
  • Test (in an open row, once its keys are saved) checks the saved key against its host with one read-only call and shows the answer inline: ✓ Connected with who you are signed in as, Key rejected (401), Can't reach host, a certificate problem, or what is still missing. It refines the row's dot straight away.
  • The dot on each service is permanent and follows the latest real calls the board and its AI make with that key (the refresh, the reports, the AI briefs, Test) — you see a problem without pressing Test: green = working · orange = needs attention (wrong or unreachable URL, network, certificate, server error) · red = key rejected or access denied · no dot = never called yet. It turns orange or red as soon as a real call fails and green again as soon as one works. Hover it for Working · last OK 2h ago or Key rejected (401) since 09:14. A missing ticket or branch (a 404 on one lookup) is not a failure.
  • Behind a corporate proxy: the Test button's cloud checks (Claude, OpenAI, Gemini, Cursor, GitHub) do not go through HTTPS_PROXY — the board's server calls them directly — so where the internet is reachable only through a proxy they may say Can't reach host even though the key is fine and the AI calls themselves work.
  • A key works from the next fetch or AI call — no restart. Remove (asks twice) clears it.
Keys are written to setup/.env in your copy of the repository — git-ignored, kept out of the Docker image and never served to the browser. Running without the board? Create that file yourself with KEY=value lines (chmod 600); the names are below.

3 · Connect Jenkins

1

Save your Jenkins user and API token

In Jenkins: your name → Configure → API Token → Add new token. In the board's key dialog, open Jenkins and save your user name and the token.

2

Point the board at your projects folder

In the same Jenkins row, fill Projects folder with the Jenkins folder that holds your projects (a placeholder: https://jenkins.example.com/job/portfolios/) and press Test — it should say Root readable · N folders. The board then finds, for each repository of your tickets, its application folder and its build and deploy pipelines in every environment, and reads the latest build of the ticket's branch from each. A deploy job that takes the branch as a build parameter is understood too. Nothing is listed by hand, and the folder stays in setup/.env on your machine (it is never part of the repository).

3

Check what it found

In the repository folder run (the repository name as Bitbucket spells it):

python3 jira-intern/jenkins.py discover payments-service

It reads Jenkins (read-only, nothing is changed and no token is printed) and shows the application folders, every pipeline as multibranch, parameterised [BRANCH] or ignored, the environment it chose and which word decided it, and its link. Exit code 2 means the folder, user or token is missing; 1 means Jenkins could not be read.

4

Tune the environment names (only if needed)

Environments are recognised from words in the folder and pipeline names — dev, qa, stage (also staging, uat), demo, prod — and anything else is labelled with the pipeline's own name. If the printout shows a wrong or missing label, add the words in your personal config (a label you write replaces its default words; you can also add new labels):

"jenkins": {
  "discovery": {
    "envPatterns": { "stage": ["stage", "staging", "uat", "qa-eu"] },
    "appFolderRegex": "^{slug}(-.*)?$"
  }
}

Found pipelines are remembered for an hour (cacheMinutes), and changing these settings takes effect at once. With several pipelines in one environment the card shows one chip — the failed one if any failed, otherwise the deploy; the ticket's Proof section lists them all.

5

Or list your multibranch jobs by hand (optional)

An explicit job always wins over discovery for that repository and environment. Add a jenkins block to ~/.ai/config.json — one job URL per repository and environment. Keys are the repository slugs; the URLs below are placeholders.

"jenkins": {
  "jobs": {
    "payments-service": {
      "qa":  "https://jenkins.example.com/job/team/job/payments-service-qa/",
      "uat": "https://jenkins.example.com/job/team/job/payments-service-uat/"
    }
  }
}

Job URLs must start with https:// — an http:// one is skipped (your token is sent with every call), and the fetch log says so. The certificate is always checked; a company certificate goes in ~/.ai/ca-bundle.pem (page 09). Only as a last resort, JENKINS_INSECURE_TLS=1 in your shell before deploying (or in setup/.env) turns checking off for Jenkins alone — JIRA_INSECURE_TLS does not apply to Jenkins.

Repositories not listed are never asked. The board reads the latest build of each of a ticket's own branches per environment: result, number, tests, failing test names, the failed stage and the deploy target. Full reference: CONFIG.md and INTEGRATIONS.md.

6

Refresh

Click Refresh. Builds are re-read on every refresh, even for tickets that did not change in Jira.

4 · Connect Checkmarx One

1

Save the API key and tenant URL

In Checkmarx One: Identity and Access Management → API Keys. In the key dialog, open Checkmarx One and save the key and your tenant API URL (https, for example https://your-tenant.cxone.cloud). Add the token URL only when your sign-in host differs from the API host.

2

Which tickets are checked

Only vulnerability-fix tickets with a pull request — ones whose title, type, labels, description or acceptance criteria mention a CVE, Checkmarx, SAST / SCA, a CWE or a dependency upgrade. For each CVE, query, CWE, result link or package the ticket names, the board compares the latest scan of the PR's branch with the base branch's scan and says Fixed, Open, Not found (in neither scan — check the id) or Unknown (no scan to compare yet). Every Not found says what was read, for example “Read 412 results on the branch (SCA 380 · SAST 18); 398 on the base …”, so you can tell a wrong id from a scan that returned nothing.

3

See what each refresh did

A refresh never skips Checkmarx silently. The run notice says what happened (“Checkmarx: 3 vulnerability-fix tickets looked up … — 2 with open findings”, “not configured — missing …”, “carried forward — the API key was rejected”), the Checkmarx panel in the key dialog has a Last fetch line (grey means not configured or nothing to look up — not a fault), and a vulnerability-fix ticket Checkmarx could not look up shows the reason at the top of its Vulnerabilities group.

If the targets do not match what you expect, run this in a terminal (read-only; it prints no key or token):

python3 jira-intern/checkmarx.py diagnose PROJ-123
python3 jira-intern/checkmarx.py diagnose my-repo --branch bugfix/PROJ-123_fix --base release/2.1 --target CVE-2024-12345

It lists the project and scans considered, how many results each scan returned (by SCA / SAST, severity and status), the field names of the rows, a cross-check against Checkmarx's own scan summary, and for every target what matched or why not.

5 · Connect Dynatrace

Optional. QA and support tickets are full of Dynatrace links — the trace of the failing request, the Davis problem, the service, a log search. With Dynatrace connected, the refresh reads those links and nothing else (it never searches your tenant on its own and never writes to it) and keeps a few short facts per link.

1

Create a platform token

In Dynatrace: Account Management → Identity & access → Platform tokens → create a token with exactly these read scopes — and nothing else:

  • storage:spans:read — the spans of a trace, and request counts of a service
  • storage:events:read — Davis problems
  • storage:logs:read — error logs
  • storage:buckets:read

In the key dialog open Observability → Dynatrace and save it as the Platform token (DYNATRACE_PAT).

2

List the tenants the board may read

In the same row fill Tenants with name=tenant id pairs, comma separated, no spaces (placeholders): prod=abc12345,uat=def67890. The tenant id is the first part of your Dynatrace address — https://abc12345.live.dynatrace.com/… or https://abc12345.apps.dynatrace.com/… → abc12345 — letters, digits and - only, no dots or slashes. Only links to these tenants are ever read. A link to any other tenant is listed in the drawer as Tenant not listed and never fetched; a Dynatrace Managed link (a host that is not *.dynatrace.com) is not recognised at all. (You can instead set endpoints.dynatraceTenants in your personal config; the dialog's value wins. Real tenant ids never go in the repository.)

3

Press Test

Test sends one tiny read-only question to every listed tenant and answers ✓ Connected · 2 tenants, or says which tenant failed: token rejected, token accepted but lacks a scope (storage:events:read), or not found — check the tenant id. The tenants may also come from the config, in which case the token alone is enough to test.

4

What it reads

For each Dynatrace link in a ticket's description, comments and links (at most five per ticket), within the link's own time window (padded by five minutes, at most two hours) and with size limits on every query:

  • a trace link — that trace's spans: how many, which services, where the failure originates, the error messages, the slowest span, and the Davis problem that overlaps it;
  • a problem link — that Davis problem: status, category, duration, root cause;
  • a service link — problems that name the service and how many of its root requests failed;
  • a logs link — the most frequent ERROR lines of the trace or service in that window.

A trace or logs link that carries no absolute time window is not read (it would scan too much); the drawer says so. Everything kept from Dynatrace is scrubbed of tokens, passwords, e-mail addresses and IP addresses first. Answers are reused for a day (an hour while a problem is still active, or when nothing was found), so most refreshes do not ask again. At most 200 calls are made per refresh.

5

See exactly what the board makes of a link

In the repository folder run (read-only; it prints no token; quote the link):

python3 jira-intern/dynatrace.py inspect "https://abc12345.live.dynatrace.com/#trace;gtf=2026-02-26T13:45:00+05:30 to 2026-02-26T14:00:00+05:30;traceId=0123456789abcdef0123456789abcdef"
python3 jira-intern/dynatrace.py inspect QA-7 --no-read

It prints the tenant the link maps to, the ids and time window it understood, the exact queries it would send and — unless you add --no-read — what they return, as findings. A ticket key reads every link of that ticket as stored on the board. Exit code 2 means Dynatrace is not configured, the link is not a Dynatrace link or the ticket is unknown; 1 means Dynatrace could not be read. Behind a company certificate put it in ~/.ai/ca-bundle.pem (page 09); DYNATRACE_INSECURE_TLS=1 is the separate last resort (JIRA_INSECURE_TLS does not apply to Dynatrace). Full reference: INTEGRATIONS.md and SECURITY.md.

6

See what each refresh did

Like Checkmarx, Dynatrace is never skipped silently: the run notice says what happened (“Dynatrace: 3 tickets with Dynatrace links looked up (5 links: 4 read · 1 empty) — 2 with failed requests or problems”, “not configured — missing …”, “carried forward — the token was rejected”), the Dynatrace panel has a Last fetch line (grey means not configured or nothing to look up), and a ticket whose links could not be answered shows the reason at the top of its Linked traces & problems group. A link that could not be re-read keeps its earlier answer, marked stale with when it was last read.

7 · Troubleshooting

Start with the Test button in the service's row: it tells you straight away whether the saved key and URL work.

SymptomFix
Test says Key rejected (401)The host answered but refused the key: it was mistyped, has expired or was revoked. Create a new one and Save it. Atlassian Cloud also needs the account e-mail.
Test says Access denied (403)The key is valid but lacks permission for that read — give the token read access (Bitbucket: project read; Jenkins: Overall/Read and Job/Read).
Test says Can't reach hostThe board's server cannot reach that address: VPN off, a typo in the base URL, or (in Docker) no route from the container. Hover the result to see the host and the error.
Test says Certificate not trustedThe host uses a company certificate. Put the company root CA in ~/.ai/ca-bundle.pem (or point JIRA_CA_BUNDLE at it) — see page 09.
Test says Not found (404) or Redirected to …The base URL points at the wrong place, or at a sign-in page. Use the API host itself (for Jira, the address you see before /browse/).
Test says Not configuredIt names what is missing — a key, the base URL (the dialog or endpoints.* in your config), a Jenkins projects folder, or a job URL in jenkins.jobs.
No build chipsAre both Jenkins keys saved and the Projects folder set (run python3 jira-intern/jenkins.py discover <repo> to see what is found) or the repository listed in jenkins.jobs with an https job URL (http ones are skipped)? Is the branch name in the ticket's PR or branch list? A branch with no build simply shows nothing.
"Jenkins unreachable — builds carried forward"The container can't reach Jenkins or the token was refused (401/403). Check VPN / DNS, the token, and a company certificate in ~/.ai/ca-bundle.pem (page 09). The last known builds stay on the cards, marked stale in their tooltip, and the report's CI gate says Not verified until Jenkins is read again.
"Checkmarx: … carried forward — …" (unreachable, key rejected or call budget used up)Check the API key, that the base URL is https, and the token URL if your sign-in host is separate. Previous results stay, and each affected ticket says why at the top of its Vulnerabilities group.
"Checkmarx not configured — add the URL and key in API keys"Save CHECKMARX_BASE_URL and CHECKMARX_API_KEY in the key dialog (the run notice names whichever is missing), then Refresh. It stays grey, not red, until you do.
Every target says Not foundRun python3 jira-intern/checkmarx.py diagnose <KEY>. The usual causes: the scans returned no results of that kind (the “Read N results” line says how many), the ticket names ids that are not in this repository, a package already at the target version in the base scan (the detail says “already at …”), or — for a merged pull request — the base scan was taken after the merge (the board then uses the last base scan from before it).
Every target says UnknownThe PR's branch has no completed scan yet (or none that ran SCA for CVEs / packages, SAST for queries), the base branch has none, the branch was last scanned before the base (rescan it), the ticket names a per-scan result id instead of a similarity id, or no Checkmarx project is named exactly like the repository.
"Dynatrace: … carried forward — …" (unreachable, token rejected or call budget used up)Check the platform token and that the container can reach <tenant id>.apps.dynatrace.com (VPN, DNS, a company certificate in ~/.ai/ca-bundle.pem). Previous answers stay, marked stale, and each affected ticket says why at the top of its Linked traces & problems group. A rejected token is the one red state: create a new platform token and Save it.
"Dynatrace not configured — add DYNATRACE_PAT and DYNATRACE_TENANTS in API keys"Save the platform token and at least one tenant (the run notice names whichever is missing). It stays grey, not red, until you do.
A link says Tenant not listedThe link's tenant id is not in Tenants, so it was never contacted. Add it (name=tenant id) if you want it read. (Dynatrace Managed links, /e/…/, are not supported.)
A link says Nothing found, or is not readRun python3 jira-intern/dynatrace.py inspect "<link>". Usual causes: the trace is older than the tenant keeps it or belongs to another tenant, the link has no absolute time window (a trace or logs link without one is not read), the tenant refused a query (a missing scope shows as Access denied in Test), or logs are not ingested.
A key row stays grey after SaveA required key of that service is still empty, or saving failed — see "could not write setup/.env" on page 09.
